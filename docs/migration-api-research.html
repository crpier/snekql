Interface research / SnekQL 0.5

Keep the API. Fix the history.

SnekQL does not need an Alembic clone. It needs to store migration order and checksums, reject history that is not an exact prefix of the declared chain, and report what each call applied.

01 / Verdict

Keep the call. Enforce its contract.

The ordered mapping is not the weak part. The history table records only names, then treats any subset of those names as valid.

Retain await db.migrate(dict[str, str]). Snapshot the mapping before the first await. Add an ordinal and SHA-256 checksum to each history row, require applied history to equal an exact prefix, return a result, and add db.verify_migrations(...) for replicas that must not mutate schema. On SQLite, make each body and its history insert one BEGIN IMMEDIATE transaction.

Borrow now

History integrity

Flyway, Liquibase, Prisma, and SQLx validate applied content. Django and Goose reject inconsistent or missing predecessors. SnekQL needs both checks.

Preserve

Raw SQL and one chain

Hand-authored SQL, explicit migrate, and separate model verification fit the project. None of the reproduced failures requires changing those decisions.

Do not copy

Framework-sized machinery

Down migrations, branch graphs, generated operations, repeatables, and target versions solve workflows SnekQL does not claim to own.

02 / Current contract

Small and readable, but unable to enforce its own rules.

Today, callers provide all identity and ordering facts at each call. The database retains too little information to prove those facts stayed true.

MIGRATIONS = {
    "001_create_user": 'CREATE TABLE "user" (...) STRICT',
    "002_add_status": 'ALTER TABLE "user" ADD COLUMN "status" TEXT',
}

await db.migrate(MIGRATIONS)  # -> None
await db.verify([User])

The neutral runner computes pending work as mapping keys - applied names, then iterates the mapping. This is compact, but set membership cannot represent sequence. See the current runner, migration documentation, and ADR 0001.

Depth assessment. The public call has good depth. Replacing the mapping with revision classes would enlarge the interface without fixing history integrity by itself. The module should absorb validation and observability instead.

03 / Validation lab

The current model can certify divergent databases as complete.

These are executable observations from SnekQL's current branch, not hypothetical edge cases. Temporary SQLite databases and the neutral runner were used so no repository data changed.

1

A hole is applied out of order

CriticalReproduced

One release applies 001, 003. A later release declares 001, 002, 003. The existing database skips 003 and applies 002 after it. A fresh database applies 002 before 003. Both histories contain all three names.

Existing database
['003', '002']
Fresh database
['002', '003']

Required fix: applied rows must be an exact prefix of the declaration, including stored ordinal. A checksum alone does not catch this.

2

An edited body is silently accepted

CriticalReproduced

A migration named 001_seed first creates a TEXT column. Its body is edited to create INTEGER. Re-running against the existing database skips it by name; replaying on a fresh database uses the edited body.

Existing schema
TEXT
Fresh replay
INTEGER

Required fix: store and compare a checksum of the exact UTF-8 body for every successful migration. Fail before executing pending SQL when any applied body differs.

3

SQLite writer serialization is not a migration lock

HighReproducedEngine constraint

Two SQLite connections were held at a rendezvous after both read an empty history. Both then attempted the same non-idempotent CREATE TABLE. One succeeded and one raised MigrationError: table race already exists. The busy timeout waited on individual writes, but did not make the read-check-write flow atomic.

Outcomes
['success', 'MigrationError: table race already exists']
History
[('001_create_race',)]

SQLite documents one simultaneous writer, not ownership across separate autocommit statements. BEGIN IMMEDIATE acquires the write transaction before the history read. A competing runner then waits according to busy timeout, acquires the write transaction after commit, and re-reads the completed row.

A prototype gave outcomes ['applied', 'skipped'] for two simultaneous runners, and a non-idempotent counter changed from 0 to 1. When history insertion was forced to fail after a body created a table, rollback removed the table.

Required fix: run SQLite's history read, one pending body, and its history insert in one BEGIN IMMEDIATE transaction. Repeat from a fresh history read for the next pending body. This serializes cooperating runners without changing the existing per-migration failure boundary.

4

Runtime scaffolding mutates history

CriticalReproduced

Public examples call scaffold([User]) inside the mapping even though the documentation says to paste and own its output. After adding a model column, that call changes the old migration body. Existing databases skip the changed body and apply the new ALTER; fresh databases create the column from the changed scaffold and then fail when the ALTER adds it again.

Existing database
success
Fresh database
MigrationError: duplicate column name: status

A scaffold with indexes emits multiple semicolon-terminated statements, while SQLite's execute path correctly accepts one statement. The migration docs say to split the output into separate bodies, but runtime examples pass the complete scaffold string as one body.

Required fix: examples must paste literal scaffold output and give each statement its own migration name. Do not switch SQLite to executescript: Python's driver commits a pending transaction before running a script, which would release the lock before the body and history row are recorded.

5

Model verification cannot prove migration currency

HighReproduced

A replica had the schema from 001_create_user but not the data-only 002_seed_system_user. db.verify([User]) passed while the expected row count stayed zero. Defaults, checks, triggers, views, and data migrations have the same blind spot because structural verification intentionally does not inspect them.

Schema verification
passed
Expected migration count
2
Actual seeded rows
0

Required fix: non-migrating replicas need a read-only verify_migrations verb in addition to model verification.

Invariant check

The proposed history predicate was exhaustively checked over all 65 ordered subsets of a four-migration chain. Only the five valid prefixes, including the empty prefix, were accepted. Reordering and body mutation were rejected. This is a small state model with a complete test oracle:

actual_history == expected_history[:len(actual_history)]

SQLite transaction check

The transaction design was exercised against two separate aiosqlite connections in autocommit mode. Both started together and used BEGIN IMMEDIATE before reading history. The second runner waited, then skipped the body after observing the first runner's commit. A separate DDL test forced history insertion to fail and confirmed that rollback removed the table created by the body.

Patterns worth taking

Applied source must still exist

Flyway, Prisma, Knex, SQLx, and dependency-based systems reject or report applied migrations that the current source no longer explains.

Mutation should be machine-detected

Checksums convert an append-only convention into an invariant. This matters more in SnekQL because verify cannot see all schema or data effects.

Out-of-order needs an explicit decision

Flyway and Goose make it opt-in; Ecto can make it fatal. SnekQL promises one canonical linear chain, so it should reject it with no escape hatch.

Read-only inspection is separate

Alembic current-head checks, Django plans, Flyway info, Ecto status, and SQLx iteration let deployments inspect without applying.

06 / Proposed contract

A linear chain that can prove it is the same chain.

The proposal makes the existing append-only rule executable. It does not infer schema changes, parse migration names as versions, or add rollback behavior.

Caller interface

MIGRATIONS: dict[str, str] = {
    # Literal output previously copied from scaffold([User]).
    "001_create_user": 'CREATE TABLE "user" (...) STRICT',
    "002_index_user_email": (
        'CREATE INDEX "ix_user_email" ON "user" ("email")'
    ),
    "003_add_status": 'ALTER TABLE "user" ADD COLUMN "status" TEXT',
}

# Deployment job: validates history, applies only the pending suffix.
result = await db.migrate(MIGRATIONS)
assert result.applied == ("003_add_status",)
assert result.already_applied == (
    "001_create_user",
    "002_index_user_email",
)

# Non-migrating replica: read-only and requires the full chain to be current.
await db.verify_migrations(MIGRATIONS)
await db.verify([User])

History schema

ColumnPurposeCorrectness role
positionOne-based insertion ordinalDetects reordering and holes; unique and not null
nameCaller-selected stable identityDetects rename, removal, or replacement; unique and not null
checksumLowercase SHA-256 of exact UTF-8 SQLDetects any body mutation; fixed 64 characters
applied_atServer-side UTC timestampObservability only, never ordering

Exact bytes are the right first checksum contract. Whitespace-only edits will fail. That is acceptable because an applied migration is immutable, and normalization would create a second language for deciding which SQL edits count. Position and name remain separate columns, so a chained fingerprint adds encoding and versioning rules without detecting another failure.

Backend DDL must enforce positive unique positions, exactly 64 lowercase hexadecimal checksum characters, and byte-exact name comparison. On MariaDB, do not rely on a padded text collation to distinguish names or checksums.

Apply algorithm

  1. Synchronously snapshot the mapping into an immutable internal tuple. Validate every item before acquiring a connection or awaiting: non-empty names, a backend-neutral 255-character name limit, and non-empty SQL. Do not return early for an empty mapping; it must fail against non-empty history.
  2. Build expected rows by enumerating the snapshot and hashing each exact body.
  3. Acquire backend serialization. MariaDB keeps its connection-scoped GET_LOCK. SQLite starts BEGIN IMMEDIATE before each history read.
  4. Ensure or upgrade the history table, then fetch rows ordered by position.
  5. Require actual == expected[:len(actual)]. Any missing source row, hole, reorder, rename, or checksum mismatch fails before pending SQL runs.
  6. Execute only the next pending body and record position, name, checksum, and timestamp. On SQLite, commit those two writes together and repeat from a new BEGIN IMMEDIATE history read. On MariaDB, keep GET_LOCK and commit the body and row together when the engine permits it.
  7. Return immutable tuples of names applied by this call and names it found already applied.

Read-only verification

verify_migrations runs the same declaration and history checks without creating a table, taking a migration lock, or executing SQL. It also requires the history length to equal the declared chain length. A replica with pending, edited, removed, reordered, or unknown migrations fails startup.

Migration integrity

verify_migrations

Proves the database records the exact chain shipped by this build. It covers data migrations and schema details that model inspection cannot see.

Structural compatibility

verify

Proves the live tables inspected by SnekQL match current model structure. It catches manual drift even when history says migrations ran.

One statement and scaffold

Keep each SQLite mapping value to one persistent DDL or DML statement against the main database. This avoids SQL splitting and lets execute keep the body and history insert inside the same transaction. Reject transaction control, VACUUM, ATTACH, DETACH, connection-local PRAGMAs, and temporary objects. Verify that the connection is still in a transaction before inserting history. MariaDB may continue to accept multiple statements, but its body and history row remain non-atomic when DDL implicitly commits.

scaffold remains a dev-time printer. Documentation and examples must paste its literal result into committed migrations, with the table and each index assigned separate names. Calling scaffold([CurrentModel]) at runtime makes old history depend on today's model and must not be presented as valid usage.

Concurrency promise

MariaDB

Keep the strong guarantee

GET_LOCK holds one connection across preflight, apply, and recording. MariaDB documents that the lock survives commits and releases on connection termination. It coordinates cooperating runners on one server, not writers that bypass the lock or connect to a different writable cluster node. Cleanup must shield RELEASE_LOCK, check its result, and discard the connection if release cannot be confirmed.

SQLite

Use the write transaction as the lock

BEGIN IMMEDIATE must precede the history read. One body and its row then commit together. Repeating this transaction per pending body preserves partial-chain progress while making concurrent cooperating runners safe.

Failure contract

Keep forward retry and the idempotent-body requirement for MariaDB. Its DDL causes implicit commits before execution, so no portable interface can promise atomic body plus history or exactly-once body execution. Do not commit the body before inserting history: DML on transactional tables can then commit with its row, while DDL retains the unavoidable crash window. Recorded rows are skipped, but a crash after DDL and before history insertion may rerun the body.

SQLite can make one statement and its history row atomic, so a failed body or history insert rolls back both. Cleanup must handle cancellation and commit-time SQLITE_BUSY without returning a connection that still holds a write transaction. Because SnekQL uses WAL, scope the atomicity promise to the main database; attached-file transactions are not crash-atomic with main.

History mismatch should use a distinct integrity exception, not MigrationError, which currently means a body failed. Definition errors should name the invalid migration before database work starts.

ADR impact. The SQLite transaction and combined MariaDB DML commit amend ADR 0001's blanket non-atomicity rule. BEGIN IMMEDIATE also replaces ADR 0002's SQLite best-effort claim. Raw SQL, explicit migration calls, forward retry, and MariaDB's advisory lock remain unchanged.

07 / Rollout and tests

Ship the invariant before adding authoring features.

The history table is persisted state from SnekQL 0.4, so its upgrade deserves more care than the Python return type.

Phase 0
Correctness copy

Correct the current SQLite concurrency claim. Replace every runtime scaffold([Model]) migration example with literal SQL split into one named migration per statement. Keep the one-statement SQLite contract.

Phase 1
History v2

Add position and checksum, exact-prefix preflight, integrity errors, SQLite per-migration transactions, the MariaDB DML commit improvement, MigrationResult, and verify_migrations. Amend ADRs 0001 and 0002 with the new backend-specific guarantees.

Phase 2
Observe demand

Only then consider a read-only status object or SQL directory loader. Both can adapt into the same validated chain without changing the runner.

Legacy history adoption

Old rows have no trustworthy application order or historical body. That information cannot be reconstructed after the fact. A non-empty v1 table should make an ordinary migrate call fail with instructions to opt in once, for example with adopt_legacy=True. Adoption means "trust this declaration as the baseline," not "verify what ran."

  1. Run under backend serialization and require legacy_names == set(declared_names[:len(legacy_names)]). Reject unknown names, holes, inserted predecessors, and an empty declaration with non-empty history.
  2. Only after explicit consent, assign positions and checksums from the current immutable snapshot. Return and log that legacy content was adopted rather than verified. An empty v1 table can upgrade without consent because it asserts no historical body.
  3. Upgrade SQLite atomically under BEGIN IMMEDIATE. Make MariaDB's schema transition a restartable state machine that recognizes only the exact v1, final v2, and known intermediate shapes. Never overwrite a non-null checksum.
  4. After adoption, enforce full v2 checks on every call. verify_migrations must fail on v1 and never adopt. Do not expose a general repair or checksum-clear method.
Irreducible limit. Even when all old names match a prefix, old history cannot prove they originally ran in that order or with the current SQL. Applied timestamps are observability fields and cannot reconstruct those facts. During the cutover, only the upgraded migrator may run: an old process can execute a body against the v2 table and then fail to write its name-only row.

08 / What not to add

Useful elsewhere does not mean useful here.

Down migrations and rollback targets

Raw SQL down bodies double authoring work and cannot restore deleted data. MariaDB DDL cannot roll back atomically. Production application rollback also needs expand-contract compatibility, not only reverse DDL. Prefer a new forward repair migration.

Revision dependencies and branch heads

SnekQL defines one canonical chain per code version. A stored ordinal and strict prefix make branch conflicts fail visibly. Teams can resolve them in source control without making every caller learn topological migration semantics.

Autogeneration and schema diffing

This remains contrary to ADR 0001, especially for SQLite table rebuilds. The research found no failure that generation would solve. Checksums and history validation strengthen hand-authored SQL without changing authority.

Repeatable migrations

Flyway and Liquibase use checksum changes to reapply views or procedures. SnekQL's current domain says each migration runs once. Adding a second identity mode would complicate prefix semantics and should wait for a concrete use case.

Durable started and failed states

Prisma, golang-migrate, and SQLx persist incomplete work so an ambiguous crash cannot trigger an automatic retry. That is useful for MariaDB DDL, but it changes the current forward-retry contract and requires operator actions such as retry, mark applied, or mark pending. Do not add dirty state without designing and shipping those recovery operations as one feature.

Public repair, force, mark, or stamp

These are necessary in tools that record dirty state or adopt arbitrary databases. They can also bless divergence. The one-time v1 adoption flag accepts only SnekQL's exact legacy schema and prefix set; it is not a general repair method. Future repair behavior should start with an operator workflow, not a convenience method.

Dry-run SQL generation

The caller already owns the exact raw SQL, so rendering it again has little value. A future status snapshot may list pending names, but it must state that another migrator can change the database after the read.
