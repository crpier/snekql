## Regression fixes and lazy-mode boundary

The migration is not just syntax replacement:

1. Backend dialect registration and the default SQLite config factory are
   explicitly resolved at namespace initialization. Lazy imports alone do not
   execute registration side effects. Shared test codecs bind their dialects
   directly instead of depending on incidental module-import order.
2. SQLite initialization catches a deferred missing driver during the runtime
   call, and its pool does not resolve the driver's error class while handling
   a failed import before any connection exists. The existing installation-hint
   regression passes.
3. Native deferred annotations avoid exposing unresolved lazy proxies to runtime
   validation. Invalid config values continue to raise domain exceptions rather
   than silently bypassing numeric constraints.
4. Former function-local library imports move to module-scope lazy imports. Root
   package import and documentation CLI help avoid initializing backends.
5. Fresh subprocess tests cover package metadata, backend loading, forced-lazy
   query compilation for both backends, config rejection, and CLI import
   isolation. Built-wheel smoke runs explicitly pass the flag too.

**Unfiltered complete-suite execution is blocked by Hypothesis itself.** Both
locked Hypothesis 6.168.1 and a temporary candidate 6.168.5 fail their own
strategy-export assertion under `-X lazy_imports=all`; the latest patch does not
fix it. No Hypothesis upgrade is retained. `scripts/run_lazy_tests.py` installs
only a test-process filter for imports whose **importer is Hypothesis or
OpenTelemetry SDK**. Locked SDK 1.45.0 and candidate 1.45.1 independently fail
when reifying the exported `HistogramDataPoint` under the flag, due to a
metrics aggregation/point dataclass import cycle. Neither patch candidate fixes
the corresponding incompatibility; neither upgrade is retained. No
snekql, test, stdlib, OpenTelemetry API, or other dependency imports are exempted;
the library never installs a filter. The runtime's global mode stays `all`.

The interpreter flag does not propagate automatically to subprocesses. The
complete-suite flag applies to its collection/execution process; the packaging
and wheel regressions separately exercise fresh child processes with the actual
flag and no filter. See [lazy-import guidance](../lazy-imports.md).

At the maintainer's direction, only ty remains an active typing gate. The
follow-up cleanup removes secondary-checker runners, stored assessments, and
checker-selection CLI options; the positive/negative ty contracts remain intact.

## Observed environment failures and held work

- One initial forced run stalled in native MariaDB bootstrap in a benchmark
  subprocess, not Python import execution. Retained temporary server data had
  consumed about 13 GiB of the 16 GiB `/tmp` tmpfs. The run was stopped, owned
  processes shut down, and inactive directories moved after checking command
  lines/open files; error logs were preserved before removing owned data.
- Two `uv python install 3.15.0 --no-bin` attempts aborted with SIGABRT during
  this period, on both uv versions. `coredumpctl` confirmed the commands and
  unsymbolized uv abort stacks; there was no recorded cgroup OOM kill. Root cause
  is not established. Retrying after reclaiming temporary storage succeeded;
  do not interpret this as proof of a particular crash cause. No core dumps
  were exported into repository artifacts.
- A disk-backed retry placed `TMPDIR` inside `.git`, contrary to the project's
  typing-temp guidance. Ty ignored rendered callers there, yielding missing
  negative diagnostics. A focused control outside the checkout passed, and the
  final full forced suite was rerun with an external private temporary directory.
  No typing assertions or diagnostic expectations were weakened to hide this.
- A subsequent complete-suite attempt reached the optional OpenTelemetry tests
  and failed collection on the SDK metrics cycle described above. A focused
  19-test regression run passes after the test-only SDK filter; the complete
  suite is rerun with that filter, with every library import still lazy.
- The initial release-candidate runs and these interrupted retries are not
  counted as successful final runs. Local logs and native server error logs are
  retained under `.git/dependency-review/python315/`.
- Latest unrelated candidates remain out of scope: FastAPI 0.143.0, OTel
  1.45.1/semantic conventions 0.66b1, Ruff 0.17.0, SQLAlchemy 2.1.4, tzdata 2026.5,
  and ty 0.0.85 (held by its explicit supported-checker pin). The final upgrade
  dry run lists the compatible unpinned candidates. PyMySQL's existing
  `<1.2.1` compatibility cap is unchanged; driver upgrade review remains separate.
- No macOS/Windows, system-library SQLite 3.45.1, other MariaDB release series,
  free-threaded Python, uvloop/Trio, performance claim, soak run, or publish was
  certified locally. Their configured CI targets still need to run on the PR.
- GitHub authentication blocks issue/PR creation. Nothing is merged, tagged or
