API comparison · 22 September 2026

Does snekql make sense beside SQLModel?

Yes, for a narrower audience. SQLModel makes ordinary application code easier to start. Snekql asks for more declarations in exchange for explicit database work and stronger checks at specific boundaries.

Reviewed snekql 0.7.0 at 354866833545, SQLModel 0.0.45 documentation and package metadata, and SQLAlchemy 2.0 documentation. Interfaces only. No implementation inspection or performance testing.

My recommendation: keep snekql, but do not sell it as a simpler SQLModel. Its best argument is an async query API with immutable rows, validated results, explicit write scope, and generated values represented accurately in types.

For a typical FastAPI CRUD service, I would start with SQLModel. For a team that wants explicit SQL without tracked objects, I would compare snekql against SQLAlchemy Core before deciding. Core is the more serious alternative.

1. SQLModel wins the first five minutes

Both libraries let you declare a table as a Python class. SQLModel uses ordinary field annotations and infers common database types. Snekql makes you declare storage and distinguish application-created rows from database-fetched rows. That distinction is useful, but the first model is visibly harder to read. [1] [9]

SQLModel

from sqlmodel import Field, SQLModel

class User(SQLModel, table=True):
    id: int | None = Field(
        default=None, primary_key=True
    )
    email: str
    status: str = "active"

Almost a plain data class. You only need special syntax for the generated primary key.

Snekql · SQLite

from snekql import sqlite as sql

class User[S = sql.Pending](
    sql.Model[S, "User[sql.Fetched]"]
):
    id: sql.GenCol[int] = sql.Integer(
        primary_key=True,
        auto_increment=True,
        default=sql.PENDING_GENERATION,
    )
    email: sql.Col[str] = sql.Text()
    status: sql.Col[str] = sql.Text(
        default="active"
    )

The state parameter, self-reference, column wrapper, storage constructor, and generation marker all need explaining.

Examples compare caller-facing patterns, not complete runnable applications. Imports are local to each example family; setup and migration code are omitted unless relevant. The primary-key declarations do not promise identical SQLite ID-reuse behavior.

What the extra syntax buys

In SQLModel's usual declaration, user.id remains statically int | None even after a database read. Snekql returns User[Fetched], where that generated ID is an int. The original pending object does not change after insertion.

That is a real improvement for functions that require a database-generated ID. But “fetched” does not mean the transaction committed, the row still exists, or the data is current. It describes how the value was obtained, not a permanent database guarantee.

Snekql also exposes storage choices directly. A UUID stored as text is visibly different from one stored as bytes. SQLModel favors inference, with SQLAlchemy types available when needed. Snekql's explicitness helps schema review, but its docs say impossible storage/type pairings can still fail during encoding or decoding rather than at declaration time. More syntax does not prove every declaration is valid.

API request models are a separate problem

SQLModel has a particularly good story for FastAPI. A shared base can feed separate create, table, and public-response models. The public model can require id: int without changing the table model's optional ID. This addresses response typing, though it does not change the fetched table object's type. [4]

Snekql's pending/fetched distinction does not replace request and response schemas. Applications still need to reject forbidden input fields and exclude private output fields. Its service recipes use separate validated input data. For routine HTTP endpoints, SQLModel offers a more direct path. [13]

Validation needs precise claims

SQLModel supports explicit model_validate(...) and Pydantic request/response validation. That is different from promising that every ORM-loaded row goes through the same validation. Snekql documents validation of fetched values and strict validation of named result models. It also exposes an option to skip some source validation, so “everything is always validated” would overstate its contract.

There is no longer a clean “snekql handles UTC, SQLModel does not” distinction. SQLModel 0.0.45 now defaults datetime storage to a UTC-aware type, rejects naive database parameters, and warns that existing data may need migration. Snekql's UtcDatetime and ZonedDatetime remain useful explicit choices, especially when the timezone identity itself matters. [8]

2. Queries are close. Object behavior is not.

SQLModel · synchronous tutorial style

from sqlmodel import Session, select

with Session(engine) as session:
    users = session.exec(
        select(User)
        .where(User.status == "active")
        .order_by(User.email)
        .limit(20)
    ).all()

Snekql · async runtime

async with db.transaction() as tx:
    users = await tx.fetch_all(
        sql.select(User)
        .where(User.status.eq("active"))
        .order_by(User.email.asc())
        .limit(20)
    )

SQLModel's comparison operators look familiar. Snekql's .eq(), .gte(), and .eq_col() are more wordy, but tell the editor whether you mean a value comparison or a column comparison. SQLModel sometimes needs col(User.name) to expose SQL methods or resolve annotation complaints. Neither approach eliminates all type-checking friction. [2]

SQLModel's exec() is a genuine convenience. For a single model selection it removes the extra .scalars() step used with SQLAlchemy's execute(). Snekql instead puts result consumption directly on the transaction.

Similar-looking methods with different jobs
IntentSQLModelSnekql
Exactly one rowsession.exec(query).one()await tx.fetch_one(query)

The last row reveals a naming trap. SQLModel's .all() consumes results. Snekql's .all() declares that an unfiltered query is intentional; it does not execute anything. Both can enforce “exactly one,” so that check is not a unique snekql advantage.

Insertion exposes the main design difference

SQLModel

with Session(engine) as session:
    user = User(email="ada@example.com")
    session.add(user)
    session.commit()
    session.refresh(user)

The session tracks the object. Generated values become available on that same object. This is the documented beginner pattern, not a claim that every insert requires a refresh.

Snekql

pending = User(email="ada@example.com")
async with db.transaction() as tx:
    created = await tx.execute(
        sql.insert(pending).returning()
    )

The insert returns a new fetched value. The pending value stays unchanged. Successful transaction exit commits.

SQLModel's behavior is convenient, but brings session rules. Objects normally expire after commit; later attribute access can cause a database read. Pending changes may be sent before a query through automatic flushing. Those behaviors are configurable, not unavoidable defects. They still need learning. Snekql's immutable rows cannot trigger lazy relationship loading or persistence through attribute assignment. [3] [7]

Updates do not require a read first on either side

SQLModel's tutorial updates an object and commits. That is pleasant when the object is already in hand. For a direct update, SQLAlchemy's statement API works with SQLModel tables too. It would be unfair to compare only against a read/change/save sequence.

SQLModel + SQLAlchemy statement

from sqlalchemy import update

with Session(engine) as session:
    session.execute(
        update(User)
        .where(User.id == user_id)
        .values(status="inactive")
    )
    session.commit()

Snekql statement

async with db.transaction() as tx:
    await tx.execute(
        sql.update(User)
        .set(User.status.to("inactive"))
        .where(User.id.eq(user_id))
    )

Snekql's important difference is the missing-filter case. An update without .where(...) or an explicit .all() is incomplete. Its supported typing contract and runtime checks reject it. SQLAlchemy permits an unfiltered update. This guard can catch an omission; it cannot tell whether a supplied filter is correct.

Relationships trade shorter code for more behavior

SQLModel's Relationship(back_populates=...) lets you use user.team and create connected objects without manually arranging every foreign-key assignment. Snekql has foreign keys and joins, but no relationship objects or automatic persistence of an object graph. That omission is helpful for explicit reads and costly for relationship-heavy applications. [5]

Both can join without declaring a relationship. SQLModel can infer a join condition from an unambiguous foreign key. Snekql asks for an explicit on=.... Its whole-model left joins type the missing right-hand row as optional. For aliases, SQLAlchemy uses aliased(User); snekql also requires a role class and column access through alias.column(User.id). That is extra ceremony on a common SQL task.

Named results are one of snekql's better conveniences

from pydantic import BaseModel

class UserSummary(BaseModel):
    id: int
    email: str

query = sql.select(User).project(
    UserSummary, id=User.id, email=User.email
).all()

async with db.transaction() as tx:
    summaries = await tx.fetch_all(query)  # list[UserSummary]

The query names the output model, binds its fields, and validates the result. SQLAlchemy can select labeled columns and return mappings, then the application can call UserSummary.model_validate(row). It can achieve the same outcome, but the mapping and validation are another application step. Snekql's named projections also avoid its eight-slot positional result limit.

3. SQLAlchemy makes the feature gap substantial

SQLModel is not limited to its tutorials. Its models work with SQLAlchemy statements. Advanced patterns may lose some SQLModel-specific typing convenience, which its own documentation acknowledges. The table credits those capabilities to SQLAlchemy rather than pretending SQLModel has a separate API for everything. [2] [6]

Do not mistake a smaller API for uniformly easier work

Snekql makes supported queries predictable, but some ordinary extensions are awkward. Its arithmetic excludes division and mixed integer/real column expressions. Recursive queries, rankings, and unions require raw SQL today. A growing reporting workload reaches that boundary sooner than a CRUD service.

Raw SQL keeps those tasks possible, but it gives up part of the builder's value. Parameters use native driver conventions, table codecs do not automatically decode raw results, and a result validator cannot prove the SQL answered the intended question. SQLAlchemy can express much more of this work without leaving its statement API.

Migrations favor different working habits

Snekql packages deployment checks into a coherent workflow: connect, apply reviewed SQL, verify migration history, verify supported schema facts. Its schema check is deliberately partial, not proof of all defaults, CHECK constraints, triggers, or data invariants.

Alembic offers broader schema-change tooling and candidate migration generation. Its documentation requires human review and lists detection limits, including renames. SQLModel's easy create_all() is not a replacement for either migration workflow. For long-lived applications, compare snekql with SQLModel plus Alembic, not just the SQLModel quick start. [14]

4. “No ORM” is not enough of a reason to exist

SQLAlchemy Core already builds and executes explicit SQL without an ORM session, object tracking, or lazy relationships. It supports async connections too. This removes several disadvantages that make snekql look attractive beside SQLModel's session tutorials.

from sqlalchemy import select

# users is a SQLAlchemy Table; engine is an AsyncEngine.
async with engine.begin() as connection:
    result = await connection.execute(
        select(users.c.id, users.c.email)
        .where(users.c.status == "active")
    )
    rows = result.mappings().all()

Transaction ownership is clear here. No attribute access loads a relationship. No object mutation silently becomes a write. SQLAlchemy Core also avoids snekql's current limits on query composition. [6] [7]

What remains distinctive is the package of choices snekql makes for you:

  • A table declaration doubles as a validated row contract, with generated-field types changing between pending and fetched values.
  • Named query outputs include decoding and model validation rather than leaving that assembly to each application.
  • The API rejects missing row scope and mixing backend families at supported static boundaries, with runtime checks for dynamic callers.
  • Deployment verification, redacted inspection, deadlines, and uncertain-commit reporting share one documented runtime.

These are useful defaults and integrated contracts. Most can be approximated with SQLAlchemy, Pydantic, and application conventions. Snekql makes sense when maintaining those conventions costs more than accepting its smaller feature set and new API.

The honest pitch is “less application code to enforce this particular set of rules,” not “SQLAlchemy cannot do this.”

5. Other costs matter more than a shorter query

Python and editor compatibility

Snekql requires Python 3.14+. SQLModel 0.0.45 supports Python 3.10+. That alone excludes snekql for many existing services.

Snekql names ty as primary and documents a tested Pyright consumer profile. Its full typing contract is not supported by mypy, and Pylance is not certified by those tests. This is honest documentation, but it is also an adoption cost. No equivalent cross-checker comparison was run for this report. [15]

Async learning costs

Snekql makes async ownership visible from the start. SQLModel users need SQLAlchemy's async guidance sooner, including loading relationships explicitly and managing expiration.

That is a documentation advantage for snekql, not proof of unique async support. Neither a SQLAlchemy AsyncSession nor a snekql transaction should be casually shared by concurrent tasks. [7]

Changing libraries later

SQLModel already uses SQLAlchemy models and statements, so adopting more SQLAlchemy APIs is a natural next step.

Snekql uses different declarations, query methods, and transaction ownership. Its docs provide incremental adoption guidance, but no bridge to borrow a SQLAlchemy connection. The two layers' transactions do not become atomic just because their context managers are nested. [13]

Backend portability

Snekql catches SQLite/MariaDB mixing, but also binds declarations to a backend. Moving a service to PostgreSQL is currently a library migration, not a connection-string change.

SQLAlchemy's dialects leave more room to grow. They do not make SQL semantics identical across databases, and backend-specific features still need review.

Operations and sensitive data

Snekql's redacted query display and commit-outcome metadata are good defaults. They encourage callers to distinguish a rejected commit from one whose outcome is unknown.

They do not make retries safe automatically or hide values in every model, traceback, and custom log. SQLAlchemy also has parameter-hiding and operational configuration; the difference is how much policy the library chooses for the application.

Testing and team familiarity

Plain immutable rows make it easier to pass data beyond a database scope without later SQL. SQLAlchemy Core mappings or separately validated response models can give the same separation.

Neither library removes the need for real-database transaction and migration tests. For hiring, help, and maintenance, SQLAlchemy's broader documented tooling is an advantage. This report does not measure community size or maintainer capacity.

Two cautions about the evidence

This is a documentation-based interface assessment, not an editor usability trial or a reliability audit. No latency, memory, or throughput advantage follows from these examples. Both “ORM overhead” and “validation overhead” need measurements on the actual workload.

I also found a documentation inconsistency in snekql: an early typing-guide example labels fetch_one() as optional, while the README and runtime contract say it returns exactly one row or raises. This report follows the latter. Contradictions around result types undermine the very advantage snekql is trying to offer. [9] [15]

What I would improve in snekql first

  1. Make the first model easier to explain. Investigate whether the repeated fetched self-type and generated-key declaration can shrink without weakening their guarantees. Do not introduce a second competing declaration style casually.
  2. Document the daily path before the exceptions. Put short create/read/update examples, result-shape rules, and a SQLModel/Core comparison near the quick start. Explain the special meaning of .all() immediately.
  3. Fix documentation contradictions before claiming stronger typing. Keep fetch_one cardinality, LEFT-join limits, and current feature tables consistent.
  4. Close common query gaps before adding ORM behavior. Named unions and ranking windows would keep more application work in the checked builder. Recursive CTEs matter where traversal is common. Prioritize from user workloads, not a feature-count contest.
  5. Prove the value on one real service. Compare model setup, a left-joined report, an atomic update, a migration, and a failed-commit path against SQLAlchemy Core plus Pydantic. Count manual validation code, type workarounds, and raw-SQL fallbacks. Ask another developer to maintain both versions.

Bottom line: snekql has a defensible purpose. Its strongest feature is a consistent set of explicit, validated database operations. Its weakest points are model ceremony, restricted compatibility, and the SQL that its builder cannot yet express. Keep the focus there. Trying to match SQLModel's relationship convenience would sacrifice much of the reason to choose snekql.
