# Test-suite performance baseline — 2026-10-25

Tracking: [improvement programme #536](https://github.com/crpier/snekql/issues/536),
[baseline #537](https://github.com/crpier/snekql/issues/537).

## Scope and result

Two unchanged full-suite runs at `395f731c58916109a21b606777fb1729543e92a8` passed **4,098 cases each**,
with no test, function-fixture, or session-fixture failures. There are 305
`test_*.py` source files; 290 contributed collected runtime cases. Some remaining
files protect static typing and must not be mistaken for valueless tests merely
because snektest collects no cases from them.

**No speedup is claimed:** this report changes no tests or library code.
The local reference is a range, not a stable performance gate. Run 2 was faster
without any code change; the wall-time range is 16.2% of the two-run mean.
Other checkout test processes were observed on this workstation, so warm-cache
effects and workload contention were not isolated. Two observations cannot
establish a percentile, a reliable median, or a causal warm-cache benefit.

## Environment and measurement method

- Linux `Linux-7.2.8-9-omarchy-x86_64-with-glibc2.44`, 28 logical CPUs.
- CPython 3.15.0; SQLite 3.53.1; MariaDB 13.0.2; snektest 0.16.0;
  ty 0.0.84; Pydantic 2.14.0; Hypothesis 6.168.1.
- Clean tracked checkout at the start; no dependency, source, or test changes
  between runs. Versions, input hashes, UTC start times, raw-report hashes, and
  exact timings are recorded in the [environment data](2026-10-25-baseline-environment.json).
- Same warning-context flag as CI, but **not the same operating system or MariaDB
  version as CI**. This does not certify the supported environment matrix.
- Sequential tests on snektest's shared event loop, with ordinary output capture
  and `--json-output`; no test concurrency or reduced property budgets.
- Fresh short private `TMPDIR` on `/tmp` tmpfs for each run; normal child SIGINT
  and SIGQUIT dispositions. A four-case CLI shutdown preflight passed before the
  full-run attempts. Background shell jobs need signal restoration; simply
  appending `&` is not equivalent to a normal foreground run.
- Existing uv, filesystem, Hypothesis, and `.snektest/mariadb-data` state was not
  cleared. These are development-checkout runs, not cold-install measurements.
- No heavy validation commands were launched by this audit during the clean
  measurements; unrelated workstation activity was not controlled.

Reproduce from the locked development environment in a foreground Bash terminal:

```bash
uv sync --locked --all-extras
run_tmp=$(mktemp -d /tmp/sqb-XXXXXXXX)
TIMEFORMAT='wall_seconds=%R'
time env TMPDIR="$run_tmp" PYTHON_CONTEXT_AWARE_WARNINGS=1 \
  uv run snektest tests --json-output > run-1.json
```

Record the exit status and timing. After a successful run, check that owned child
servers have exited, then remove **only** that newly created `$run_tmp` root.
Retain failed-run logs for diagnosis. Repeat with a fresh root and output filename.
Keep the temporary path short because Unix-domain socket paths are length-limited.
Do not delete arbitrary `/tmp/snekql-mariadb-*` directories or caller-owned data.

### What the runner's durations mean

In snektest 0.16.0, per-case duration covers the test call, including fixtures
loaded during it and context managers exited inside the test. Function-fixture
teardown performed by the runner afterward is excluded, as is final session
teardown. Session startup may be charged to its first consumer. Collection also
overlaps execution. Therefore these tables rank costs but do not separately
attribute setup, body, and teardown; wall time remains authoritative. The gap
between wall time and summed durations is not a fixture-teardown-only metric.

## Investigation findings and next slices

1. **Own temporary artifacts and surface failed setup promptly.** During the
   earlier attempts, retained MariaDB data exhausted the `/tmp` quota. A focused
   credential test failed in about 0.08 seconds with InnoDB error 122 while
   preallocating its 96 MiB redo log. Event-gated cancellation tests then waited
   for readiness that could never happen: one diagnostic case took 60.005 seconds.
   This was failure-path amplification, not evidence of an infinite deadlock.
   [Issue #542](https://github.com/crpier/snekql/issues/542) records the evidence and acceptance criteria.
   Preserve the public temporary-server retention contract; give suite-created
   artifacts an explicit owner and propagate early setup-task failures.
2. **Consolidate typing-assessment execution, not its guarantees.** The four
   typing subprocess files cost 45.84/42.96 seconds across
   171 cases. Reuse or batch compatible assessments while preserving independent
   positive controls, exact diagnostic rule/count/location checks, named failure
   attribution, and narrow focused runs. Keep representative real CLI checks.
3. **Reduce full benchmark launches.** The 61 cases in
   `tests/test_comparative_benchmarks.py` cost
   40.02/38.38
   seconds. Separate report/argument logic from representative real CLI workloads,
   retaining distinct backend and adapter integration contracts.
4. **Profile database setup and shutdown at the largest integration files.**
   Aggregate runtime and MariaDB costs dominate the suite. Before changing
   fixtures, distinguish initialization, reset, migration replay, assertions, and
   teardown. Preserve isolation and migration replay; do not introduce a
   model-direct schema shortcut. The single
   `terminate_resistant_server_is_killed` case deliberately consumes approximately
   ten seconds of real shutdown grace and deserves a controlled-grace investigation.
5. **Defer low-cost consolidation.** All 671 query cases total
   0.80/0.78 seconds. Packaging totals
   2.44/2.37 seconds. Duplicate
   setup there may be worth simplifying for maintainability, but is not a leading
   runtime opportunity. Do not reduce property budgets or delete cheap tests just
   to lower the case count.

The initial run without context-aware warnings, the quota-affected attempt that
was terminated after approximately 12m 47s, and the instrumented diagnostic run
are **excluded** from these measurements. Audit-created inactive data from those
attempts was cleaned after preserving relevant logs and recording a manifest;
other live checkouts and their data were left alone.

## Acceptance for later optimization claims

- Reproduce the same case/contract inventory, or explicitly map every replacement.
- Use TDD at agreed interfaces and targeted fault injection for important
  replacements; coverage percentages alone do not prove equivalent protection.
- Compare repeated focused workloads and unchanged/full candidate runs under
  equivalent conditions. Use an exclusive host or interleaved baseline/candidate
  measurements before attributing a noisy full-run difference to a code change.
- Count collection and all fixture failure modes, and retain complete SQLite,
  MariaDB, deadline, cancellation, and migration coverage.
- Record artifact ownership and cleanup cost when introducing a repository runner.
  Do not hide slow checks outside the default suite to claim an improvement.
